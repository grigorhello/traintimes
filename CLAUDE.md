# CLAUDE.md — Train Times

Rules every Claude session follows in this repo. If a message from Grigor in the session says otherwise, the message wins.

## Where things are

- Tickets: GitHub issues #1–#31 (issue #N = build step N, TT-100…TT-154) and the Notion board "TrainTimes · Product board" (https://app.notion.com/p/4107cd9e1320815c95bed6694390e203, database "TrainTimes tickets"). Each Notion card links its issue in the "GitHub issue" field; each issue links its card.
- Build sequence and blockers: [`docs/BUILD-ORDER.md`](docs/BUILD-ORDER.md). Do not start a ticket while a blocker is open, including an open question in `docs/DECISIONS.md` marked "needed by" that ticket.
- Decisions and open questions: [`docs/DECISIONS.md`](docs/DECISIONS.md). Follow every decision; if a ticket needs a new one, add it there in the same PR.
- Behaviour: [`design/Screen-Requirements.md`](design/Screen-Requirements.md) (its Acceptance checks are the QA list). Look: [`design/frames/`](design/frames/). Handoff files: [`design/handoff/`](design/handoff/).

## Per-ticket workflow

**Speed first (Grigor, 2026-11-07): startup style.** Build only what the ticket's acceptance criteria need; no extras, no gold-plating. Keep both reviews to a quick pass, one round unless something is actually broken, and keep PR bodies and reports short.

1. **Before writing code**, move the Notion card Status to `In progress` and make sure the GitHub issue is open and assigned, so Grigor can follow progress on the board.
2. Read the issue, its Notion card, the frames and the requirements sections it names, and `docs/DECISIONS.md`.
3. Implement on a branch. Open a PR whose body starts with `Closes #N` (or `Part of #N` while an acceptance criterion only Grigor can meet is still open), links the Notion card, and (for UI tickets) shows simulator screenshots next to the frame images.
4. Run **two separate review passes** on the PR:
   - **QA review:** correctness, edge cases, tests, build and CI pass, the ticket's acceptance criteria and Definition of done.
   - **Design review:** compare the result against the ticket's design frames and the requirements doc (layout, tokens, copy, states, light and dark).
   - **Device scope (Grigor, 2026-11-07):** test and review on **iPhone 17 Pro only**. Skip accessibility (VoiceOver, Dynamic Type, large text) and iPad layout in reviews and tests, even where an issue's Definition of done lists them (D23).
5. Fix the findings. If the first round found major issues, run one more round of both reviews. **Two rounds maximum**, then ship.
6. Comment the review outcome on the issue, then **merge the PR yourself** (squash) once the reviews are done and CI is green, and move the Notion card to `Done` (Grigor, 2026-11-07: "merge all PRs, do not wait for me"). Then continue with the next ticket in build order. Stop and tell Grigor only when you hit a blocker you cannot clear (an open "needed by" question, something only he can do, or a red CI you cannot fix).
7. Report back after each ticket: Notion card status, PR link, and the outcome of each review round.
8. **One ticket per session.** A session implements exactly one ticket. When its PR is merged, report back and stop; the next ticket starts in a new session so each one begins with a fresh context (Grigor, 2026-11-07, to save tokens). Anything the next session needs goes in this file, `docs/DECISIONS.md` or the issue, not in chat.

Notion Status values, in order: Backlog, Needs design, Design review, To do, In progress, PR review, Feature QA, Done.

## Code conventions

Set up in TT-101. Every ticket follows these; a reviewer checks them in the QA pass.

### Project

- `TrainTimes.xcodeproj`: one app target `TrainTimes`, `TrainTimesTests` (unit and snapshot, hosted in the app) and `TrainTimesUITests` (XCUITest). iOS 17 minimum, Swift 6 language mode, complete strict concurrency, warnings are errors (D1–D4).
- The project uses **Xcode 16 synchronized folders**: adding, moving or deleting a file under `Sources/`, `Resources/`, `Preview Content/` or `Tests/` needs no project edit. Do not put non-code files such as READMEs in those folders; they would be bundled (`.gitkeep`, which holds empty folders, is excluded by `EXCLUDED_SOURCE_FILE_NAMES`; delete it once a folder has files).
- To change targets, build settings or packages, edit `scripts/generate-xcodeproj.rb` and re-run it (`gem install xcodeproj`, then `ruby scripts/generate-xcodeproj.rb`; works on Linux), and commit the regenerated project. Do not hand-edit `project.pbxproj`.
- Bundle id `ca.traintimes.TrainTimes`; Display Name "Train Times" (D7).
- Info.plist keys come from `INFOPLIST_KEY_*` settings in the generator; a key with no such setting goes in `Config/Info.plist`, which Xcode merges with them (today `MetrolinxAPIKey` from the `METROLINX_API_KEY` build setting, D36, `ITSAppUsesNonExemptEncryption` NO, D47, and `UIBackgroundModes` location, D60).
- Asset catalogs live in `Resources/`: `AppIcon.xcassets` (TT-103) and `Colors.xcassets` (TT-102, the 22 token colours, with `Veil` from TT-161; `Accent` is the global accent colour). Both build settings are set in `scripts/generate-xcodeproj.rb`.
- Shared components (TT-102) are in `Sources/Design`: `StatusBadge`/`TripStatus`, `ExpressTag`, `TimePill` (gallery only since D49), `.ttPrimary`/`.ttSecondary`/`.ttText` button styles, `IconButton`, `DayCell`, `DayChip`, `SegmentedControl`, `Card`, `FreshnessLine`, `Toast`, `EmptyStateCard`, `SkeletonCard`, `TabBarStyle` (TT-104, D49: tab icons, and the classic bar before iOS 26), `GlassIconButton`/`ttGlass` (D49: Liquid Glass with a raised-surface fallback), `LineTile`/`GOLineColor` (D49: the GO line colours, keyed by line id), `PlatformPill` (TT-162, D55: the pulsing placeholder for a platform the next train is still waiting for; snapshot tests freeze it with `\.swapFrozenAt`), `GlassSwitch` (TT-168, D57: a recessed track with one glass thumb that glides, for Appearance, Time format and Demo trains; the thumb is Liquid Glass on iOS 26, a solid raised surface before it and when `\.rendersGlass` is off) and `SettingsMotion` (the Settings springs; Components take times already formatted by the one formatter. Token fonts are fixed sizes (no Dynamic Type scaling, D23).

### Architecture

- **MVVM.** Views hold layout only, no business logic. Each screen has an `@Observable @MainActor final class` view model that gets its dependencies as protocols through `init` (repositories, clock, formatter), so tests inject fakes.
- **Repositories return domain types** from `Sources/Core`, never feed or JSON types. Fixture and live implementations sit behind the same protocol (D20).
- **One time formatter** (TT-106) for every time on screen, in VoiceOver and in notifications (D17); tabular digits.
- **Schedule data** (TT-130, D35): the app reads GO Transit's GTFS feed through `GTFSScheduleRepository` (`Sources/Core/Schedule/GTFS`), which also serves the station list. `GTFSFeedStore` downloads the feed on first use, imports rail only, keeps the last good import in Application Support and refreshes it weekly. `ScheduleDependencies.app()` picks it; Xcode previews, the unit test host and UI tests get the fixtures instead. Line notices come from GO's GTFS-realtime Alerts feed (TT-132, D37), read like live status below.
- **Live status** (TT-131, D36): `GTFSRealtimeStore` (`Sources/Core/Schedule/Realtime`) fetches GO's GTFS-realtime TripUpdates feed and `GTFSScheduleRepository` maps it onto the route's trips. The Metrolinx key comes from the `METROLINX_API_KEY` build setting in `Config/Secrets.xcconfig` (git-ignored, included by `Config/App.xcconfig`); never commit it. A build without the key shows the schedule only, with no line notices. Until the key arrives, tests replay the samples in `Tests/UnitTests/Core/Realtime` (`FeedReplay`, written by `scripts/make-realtime-samples.py`; `alerts-*.pb` for line notices). UI tests that need the line notice launch with `XCUIApplication.onDelayedFixture()` and `LaunchArguments.noDismissedNotices`.
- **Alert server** (TT-140, D38, D43): `server/`, a Cloudflare Worker with D1 in TypeScript, its own project outside the Xcode project, on the Workers Free plan (10 ms of CPU per run: keep the minute cycle lean). GitHub Actions uploads the timetable daily (`.github/workflows/server-timetable.yml`). Test with `cd server && npm ci && npm test && npm run typecheck` (Node 22.18 or later, works on Linux); CI runs `.github/workflows/server.yml` when `server/`, the handoff strings or the sample feeds change. Its `notif.*` copy must match `design/handoff/Localizable.strings` word for word (a test checks). Setup, secrets and deploy: `server/README.md`.
- **Notification taps** (TT-144, D39): `AppDelegate` (`Sources/App`) is the notification centre's delegate and hands each tap's `NotificationLink` (`Sources/Core/Notifications`, parsed from the server's `tripId`/`serviceDate`/`originId`/`destinationId` or `ruleId`) to `AppRouter.open(_:)`; `RootView` opens Trip details or the Alerts tab. UI tests launch as if by a tap with `XCUIApplication.onFixtures(notification:)` (`TT_NOTIFICATION`, Debug only). The watched-trip strip reads `WatchedTripsProviding` (`Sources/Core/Alerts`), which the alert rules store conforms to.
- **Alert rules** (TT-141, D40): `AlertRules` (`Sources/Core/Alerts`), one instance made in `RootView` and shared by the bells, the alert setup sheet, the Alerts tab and the watched-trip strip. It keeps rules on device (`alerts.rules`, read once at launch) and saves them on the alert server (`HTTPAlertServer`) after registering the APNs token (`SystemPushRegistration`, fed by `AppDelegate`). `state(of:)` is the only source for On. **One alert per train card** (TT-189, D70): `alert(for:on:)`, the alert that covers a train on its day (a This-trip alert, or a Repeat alert for its usual train on one of its days), is the one lookup; the bell, Trip details (`TripDetailsViewModel(alerts:)`), the watched-trip strip and Live mode read only it, through `WatchedTripsProviding` (`isWatched(_:on:)`, switched on and On; `isAlerted(_:on:)`, switched on), which `RootView` passes to `ScheduleViewModel` and Trip details. A bell tap acts on that alert (a repeating one is switched off with its days, a left-out day is added to it), Repeat saves under the same id, and doubles are merged at launch and after each save. `AlertDependencies.app()` gives previews, the unit test host and UI tests `FixtureAlertServer` and a fixture token. UI tests set `TT_NOTIFICATIONS` (`allowed`, `off`, `notAsked`) in the launch environment and pass `LaunchArguments.noAlerts` (`TT_TOAST_SECONDS` keeps the bell's 2.5 s toast up longer); unit tests build `AlertRules` with `FakeAlertServer` (`Tests/UnitTests/Support`) and `defaults: nil` or `.ephemeral()`.
- **Alert setup** (TT-142, D41): `AlertSetupView`/`AlertSetupViewModel` (`Sources/Features/Alerts`), made by `RootView` from an `AlertSetupRequest` (Trip details, the bell, its toast). Notification permission is asked only through `AlertRules.requestPermission()`, on "Enable alerts", on the Notifications page's "Turn on notifications" (D57) or right after a ride started from "I’m on board" or the detection question's Yes (D66), never earlier. A new rule that turns On shows the check, holds `AlertSetupViewModel.confirmHold` (0.3 s, injected in tests as `hold:`) and closes the sheet (TT-166, D62); UI tests reopen it to see Manage alert. The app target has the `aps-environment` and Time Sensitive (D66; switched on for the App ID too) entitlements (`Config/TrainTimes.entitlements`). UI tests answer the iOS permission dialog through SpringBoard (`Tests/UITests/AlertSetupTests.swift`) or fix the permission with `TT_NOTIFICATIONS`.
- **Alerts tab** (TT-143, D44): `AlertsView`/`AlertsViewModel` (`Sources/Features/Alerts`), a `List` so rule rows swipe to delete (undo re-saves with the same id). Review needed comes from `AlertRules.refresh()` (`GET …/rules`), run on foreground and on opening the tab. Recent updates are `AlertUpdates` (`Sources/Core/Alerts`), notifications kept on device for 7 days (`AppDelegate` records arrivals and taps); fixture runs have none. Line notices are Schedule's (`LineNoticesProviding`). Unit tests build the model with `AlertsFixtures` (`Tests/UnitTests/Support`). **Notifications off** (TT-169, D58): `AlertsViewModel.warnsNotificationsOff` (permission `.off` and a switched-on alert, `AlertRules.switchedOnCount(on:)`) puts `notificationsOffCard` on top of the list, makes `tabDot(isSelected:hasNewUpdate:)` return `TabBarStyle.Dot.warning` (red, wins over the accent dot, nil on Alerts itself) and turns a rule that is on into the "Not delivering" row (a switch, not a chevron; paused stays Paused); `refresh()` starts the "Notifications are on" toast (`showsNotificationsOn`) when it finds the permission allowed after a warning. UI test ids: `alerts.notificationsOff`, `alerts.turnOnInSettings`.
- **Settings** (TT-105, D48: the third tab): `AppSettings` (`Sources/Core/Settings`) stores Appearance and Time format in `UserDefaults`. `RootView` applies Appearance with `preferredColorScheme` and puts `settings.timeFormatter` in the environment as `\.timeFormatter`. Screens format times with that value, never a `TimeFormatter` of their own, so a Time format change updates every time at once. A view model must not keep a formatter from `init` (a view model held in `@State` would keep the old one): the view passes `\.timeFormatter` on each formatting call, or the view model reads `settings.timeFormatter` each time. Tests pass `AppSettings(defaults: .ephemeral())` (`Tests/UnitTests/Support`), never `.standard`. **Settings pages** (TT-168, D57): `SettingsView` (`Sources/Features/Settings`) is a `NavigationStack` with the system bar hidden (a 44 pt row of its own: `GlassIconButton` back, centred title, Reset on Testing; the tab bar stays) over `SettingsMainPage` (five rows in two `SettingsCard`s: Appearance and Time format as `GlassSwitch`, Notifications with a dot status, About, Testing in TestFlight and Debug builds only), `SettingsNotificationsPage`, `SettingsAboutPage` and `SettingsTestingPage`. The rule: a card holds things you can tap, plain text is information. `SettingsViewModel` has `notificationDot`/`notificationWord` (green On, red Off, grey Off), `testingValue`/`isTestingActive`/`resetTesting()`, `alertCount` (from the shared `AlertRules`) and `turnOnNotifications()` (the iOS prompt through `AlertRules.requestPermission()`, D41 revised). Pushed pages are snapshotted directly (`SettingsNotificationsPage(viewModel:onShowAlerts:)` etc.) with `\.rendersGlass` and `\.playsSettingsMotion` false. UI tests: rows `settings.notifications`/`settings.about`/`settings.testing`, switches `settings.appearance.<system|light|dark>`, `settings.timeFormat.<device|12h|24h>`, `settings.demoTrains.<off|delays|offline|platform|ride>`, the Mock time switch `settings.mockTime` (with `settings.mockTime.<early|late|dayChange>` and `settings.mockTime.picker`), `settings.back`, `settings.testing.reset`, `settings.myAlerts`.
- **Station picker** (TT-161, D54): no sheet chooses a station. `RouteFormViewModel` (`Sources/Features/Route`) is the model for first use (`RouteFormView`, made once in `RootView`) and for Schedule (`ScheduleView` makes one each time a station row is tapped, `route:` set, so `appliesAtOnce`). `RouteCard` turns the tapped row into `StationField` (the current station is its grey placeholder with the cursor before it, nothing selected) and the swap button into the X (`RouteCard.Picking`); the card squares its bottom corners while picking (`Card(joinsBelow:)`). `StationPickerPanel` is the list hanging under it as one surface with the card (`ttAttachedPanel`, one `StackShadow` cast from the union; Recent on Schedule only, Your stations, All stations, each row with a 20 pt leading glyph and no trailing clock). On Schedule `ScheduleView.pickerLayer` adds the frosted veil (`TTColor.veil` over `.regularMaterial`) and fades the day strip. Motion is `PickerMotion` (`Sources/Design`: `.pickerPanel` clip reveal, the row fall-in stagger, `.pickerCancelButton`/`.pickerSwapButton`, `.pickerVeil`); snapshot tests set `\.animatesPickerEntrance` to false so rows are drawn settled (the layer render cannot draw the veil's blur). `pick(_:)` returns true when a Schedule pick completed the route, and the caller shows `route()`. UI tests: `schedule.from`/`schedule.to` (buttons, value = the name; text fields while picking), `route.from`/`route.to`, the X is `route.cancel`/`schedule.cancel`, the panel `stations.panel`, rows `station.<id>` (`station.yours.<id>` under Your stations) and `route.recent.<from>-<to>`.
- **Schedule screen** (TT-156, D49): the header (line row, route card, day strip, status row) is a top `safeAreaInset` over one full-height scroll view, so the timeline scrolls under the glass tab bar. There is no Now button: `RootView`'s tab binding calls `ScheduleViewModel.backToNow()` when the Schedule tab is tapped again, and a scroll request is followed by one `settleRequest` once every card is measured (unanimated on the launch's request, animated after it). A train with no live status shows "On time" (`TripStatus.init(_:isOffline:formatter:)`; the domain status stays `.scheduled`, D12/D13); only offline keeps the grey "Scheduled". The left column holds gridline times and the Now label only (no train pills). **Demo trains** (Settings › Testing, TestFlight and Debug builds, `BuildChannel.showsTesting`): `DemoScheduleRepository` wraps the repository in `ScheduleDependencies.withTesting()` and reads `DemoTrains.stored` on each call; UI tests force a mode with the launch argument `-settings.demoTrains offline` (`delays`, `off`), never by tapping, so nothing is left on the simulator. **Mock time** (TT-158, D51, same section): `withTesting()` also wraps the clock in `MockTimeClock`, which reads `MockTime.stored` on each call and runs on from the chosen moment, so every screen sees the mocked time; UI tests set it with `-settings.mockTime <seconds since 1970>` (it runs from the start of the run), and with it on the real live status is dropped. Unit tests build `SettingsViewModel(showsTesting:)` explicitly. **Day and scroll** (TT-159, D52): Schedule's `today` is the Toronto calendar day (`ServiceDay(calendarDayContaining:)`); every other feature keeps the 3 AM service day. `rollOverIfNeeded()` (minute tick, foreground poll) moves a rider on Today to the new Today at midnight; the timeline is moved by `ScrollOffsetSetter` (it sets the `UIScrollView` offset; `ScrollViewProxy.scrollTo` stayed at the top on a long timeline, so do not go back to it), and a scroll request is repeated by `rescrollRequest` (150 and 600 ms) and `settleRequest`, and the view stops repeating once the rider drags. UI tests that need a long timeline launch with `XCUIApplication.onFullDayFixture()` (`TT_FIXTURES=fullDay`) and `-settings.mockTime`. **Day strip** (TT-160, D53): it shows `pastDays` (7), then `days`, opening at Today; tile ids and `schedule.day.N` identifiers count from Today (`-1` is yesterday). **Motion** (TT-164, D61): the selected day's accent tile is drawn once under the strip (`DayCell(drawsSelection: false)`) and glides on `TTMotion.glide` when `daySelection` is bumped (a picked day, back to Today; never the midnight turn); the tapped tile presses (`DayPress`); `entranceRequest` (bumped inside `load(newTrains:)`; `awaitsNewTrains` hides the old cards from the tap, `scrollJumps` makes that scroll a jump) cascades the cards in and `nowPulse` pulses the Now dot, both drawn from the clock (`CascadeMotion`, `NowPulse`, `MotionRun`, `Sources/Design/ScheduleMotion.swift`) with their starts in `ScheduleMotionClock`, which only the moving views read (`CascadeCue`), so a start never redraws the whole timeline; the press is `dayPress` (`DayPressMotion`), a SwiftUI animation like the glide, so a slow frame after the tap delays them both; `\.playsScheduleMotion` is false in the unit test host, so snapshots draw Schedule at rest.
- **Trip details sheet** (TT-163, D56): `TripDetailsView`/`TripDetailsViewModel` (`Sources/Features/TripDetails`). `details(_:)` returns the display model (`TripDetails`): journey times (`TripDetails.Time`, the expected time with the struck scheduled one when 1 min or more late), the countdown only on `nextDepartureId`, `stopCount`, `freshnessText` per data mode, `isCancelled` (struck times, no alert button). The header is the line tile and name (`trip.title`), the close button `trip.close`, the floating alert capsule `trip.alert` (`ttGlass(tint:in:)`); the view ignores the bottom safe area so the button sits 24 pt above the screen's edge and the content ends 92 pt above it. Snapshots draw the long trip scrolled to its end with `TripDetailsView(startsAtEnd: true)`, and turn the glass off with `\.rendersGlass` (dark glass is drawn differently from one run to the next; the simulator shows the real glass). **Directions** (TT-188, D64): the link under the departure station (`trip.directions`) shows while `TripDetailsViewModel.directionsStation` is set (train not left, calls there, `Station.place` known) and opens Maps through `MapsOpening` (`SystemMapsOpener`; tests pass `FakeMapsOpener`).
- **On board** (TT-171, D60): `RideEngine` (`Sources/Core/OnBoard`), one per app (`AppDelegate.ride`, restored at launch from `onboard.ride`), with its state in `RideState` and `events()` for the nudge and the Live Activity. A ride starts only through `start(_:)`, the one place location is asked (`LocationProviding`; `SystemLocationProvider` runs `CLLocationUpdate.liveUpdates` with a `CLBackgroundActivitySession`). The trip's stops, track and station places come from `GTFSTimetable.ridePlan(for:)` (shapes.txt, rail only); a trip with no track rides on the timetable. Unit tests build `RideEngine(..., tickInterval: nil)` with `FakeLocation`, `FakeRideData`, `FakeTrainPositions` and `OnBoardFixtures` (Union to Clarkson on the sample feed with a synthetic track), and move a `TestClock` by hand.
- **On board UI** (TT-172, D63): `OnBoard` (`Sources/Core/OnBoard`, one per app in `RootView`, fed `AppDelegate.ride`) is what the screens read: Trip details takes it (`TripDetailsViewModel(onBoard:)`, nil keeps the old sheet) for "I’m on board" (`trip.onboard`, 20 min before departure until arrival, the bell beside it keeps `trip.alert`), the first-ride sheet (`RideIntroSheet`) and ride mode (`RideContent`, display model `RideDetails`, card `trip.ride`, End ride/Done `trip.endRide`); Schedule shows `RideStripView` (`schedule.ride`) in the watched-trip strip's place. Demo trains › Ride (`DemoRide`, `-settings.demoTrains ride`) first asks the train detection question (TT-175, about 22 s after Schedule shows), then plays the ride from the Yes at 6× on its own engine. Unit tests use `DemoRideRig` (`Tests/UnitTests/Support/TripDetailsFixtures.swift`, `drive(to:)`, no question: `OnBoard(makeDemoDetector: nil)`) and `TripDetailsViewModel.onBoardFixture()`; snapshots set `\.playsRideMotion` false.
- **Train detection** (TT-175, D68): `TrainMatcher` (`Sources/Core/OnBoard`, pure: the four checks and the confidence rules) run by `TrainDetector` (fixes, the trains on the route from `TrainCandidatesProviding`, later TT-179's `TrainPositionProviding`), owned by `OnBoard` (`detection`, `detect(on:demo:)`, `accept(_:)`, `decline()`). `RootView` runs it only while the Schedule tab shows in the foreground, and only with location already allowed: it never asks, and only the rider's Yes starts a ride. Schedule shows its checking strip (`schedule.detect`) or question (`schedule.question`, `.yes`, `.yes2`, `.no`) in `RideStripSlot` (`DetectionViews.swift`): the strips share one top-aligned `ZStack` so their transitions run (a `Group` hands `.animation` to the inserted view, too late), and `ScheduleView` applies `rideStripMotion(_:)` above its header inset so the timeline moves with the strip instead of jumping. Fixture runs have no detector; the demo's question is the UI test's way in. Unit tests drive a `TrainMatcher` on the synthetic track second by second (`TrainMatcherTests`), a `TrainDetector` with `FakeLocation` and a `TestClock` (`tickInterval: nil`), and `DetectionFixtures` for the display models and snapshots.
- **Arriving nudge** (TT-173, D66): `ArrivalNudge` (`Sources/Core/OnBoard`) follows a ride engine's events: `AppDelegate.nudge` the app's from launch, `OnBoard` makes one per demo ride (`followDemo`, from `setDemo` or the demo question's Yes). It schedules the two Time Sensitive local notifications through `RideNotificationScheduling` (`SystemRideNotifications`) and plays `ArrivingHaptics` and `Resources/arrive.caf` through `ArrivalFeedback` (`SystemArrivalFeedback`, app active only). A ride started through `OnBoard.start(_:on:)` ("I’m on board", or detection's Yes) asks for notifications via `OnBoard`'s `requestNotifications` (the alert rules). Unit tests call `handle(_:ride:destination:now:)` with `FakeRideNotifications`/`FakeArrivalFeedback` (`Tests/UnitTests/Support/OnBoardFixtures.swift`), or pass a nudge to `DemoRideRig.started(makeNudge:)`.
- **Strings** come from `Localizable.strings` by key (`Text("tab.schedule")`, `String(localized:)`); no literal copy in code. Keys that take values (`%@`, `%d`) are formatted, not interpolated: `String(format: String(localized: "status.delayed"), minutes)`; `Text("status.delayed \(minutes)")` looks up a key that does not exist. Times are formatted by the one formatter first and passed as `%@`.
- Swift 6 concurrency: no `@unchecked Sendable` or `nonisolated(unsafe)` without a comment saying why it is safe.

### Tests (from each issue's Definition of done)

- Unit tests for every view model and rule.
- Snapshot tests (`assertSnapshot(of:as: .image(layout: .device(config: .iPhone17Pro), traits:))`, config in `Tests/UnitTests/Support`) for every screen state the ticket touches, in light and dark. iPhone 17 Pro only; no large-text or iPad snapshots (D23). Test methods that touch views are `@MainActor`.

### Building and CI

- CI (`.github/workflows/ci.yml`) runs `scripts/ci-test.sh` on the iPhone 17 Pro simulator on the latest GitHub macOS runner on every pull request and on main. Run the same script on a Mac to test locally.
- **Snapshot references are recorded by CI**, since cloud sessions run on Linux without Xcode. Add a snapshot test without a reference and push: CI records the missing image, commits it to the PR branch as "Record reference snapshots… [skip ci]", re-runs the tests against it in the same job and posts the result as the "CI / Build and test" status on that commit, so the PR head shows green or red without a new run. Pull before pushing again, and look at the recorded PNGs in the PR diff during the design review. A changed snapshot is never re-recorded automatically: delete the old reference in the PR to have CI record the new one. References are excluded from the test bundle (`*.png` in `EXCLUDED_SOURCE_FILE_NAMES`).
- **UI test waits on slow runners**: some runners are 2 to 6 times slower than others (the UI suite took 458 s on one and 928 s on another, same tree). A query's first check takes about a second on a Mac, so a 5 s wait after a tap or a launch can time out with the right value already on screen (`RecentRoutesTests` turned main red after TT-164 this way; the app was not slower). Give such waits 15 s.
- **Glass snapshot noise**: a snapshot that draws the Liquid Glass bar (`glassSnapshotPrecision`, `drawHierarchyInKeyWindow`) can still miss its tolerance on a runner. On PR #79 `testScheduleTabLight` failed in the recording pass and passed in the re-run, and `testAlertOnDark` failed the other way round, on the same tree; on PR #117 `AlertsSnapshotTests.testAlertsDark` passed in the recording pass and failed in the re-run. A snapshot that fails in only one of the two passes is that noise: push a new commit to run CI again, and do not delete its reference. The swap button's dark glass failed `ScheduleStatesSnapshotTests` in both attempts of one run (a different state each time, and on other branches before), so that suite sets `\.rendersGlass` false like Trip details (TT-166). Before PR #124 many of these failures were the colour-encoding problem `.comparedAsRecorded` fixes (a constant 0.9159375 or similar in light, only saturated pixels off), so read the numbers before calling a failure glass noise.
- **Mock time snapshots follow the date**: the system compact date picker on Settings › Testing draws slightly differently from one UTC day to the next (its pills moved at 00:00 UTC on Nov 10 and again on Nov 11, on every branch), so `testTestingMockTimeLight`/`Dark` can fail in both passes after a midnight with no code change. Delete the failing reference in the PR to have CI record it again. A lasting fix (keeping the system picker out of the compared pixels) is not built yet.
- **TestFlight** (TT-154, D47): Actions › TestFlight › Run workflow archives `main` and uploads it (`scripts/testflight.sh`, signing through `scripts/asc-signing.mjs` with the `ASC_*` API key secrets); build number = run number, version from `MARKETING_VERSION`. Release builds are only compiled there, and on pull requests that touch its files (unsigned).
- **Squash-merge with your own commit message** (the PR title and `Closes #N`): the default squash message lists the bot's `[skip ci]` commit, and GitHub would then skip CI on main.
- **Never write a skip marker in your own commit messages**, not even to describe one: `[skip ci]`, `[ci skip]`, `[no ci]`, `[skip actions]` or `[actions skip]` anywhere in the message makes GitHub create no CI run for that push, so the PR head has no check. After every push, confirm a run started.
- When the runner image moves to a new iOS version, snapshots may drift; re-record them in one PR by deleting the `__Snapshots__` folders.
