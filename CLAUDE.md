# CLAUDE.md — Train Times

Rules every Claude session follows in this repo. If a message from Grigor in the session says otherwise, the message wins.

## Where things are

- Tickets: GitHub issues #1–#31 (issue #N = build step N, TT-100…TT-154) and the Notion board "TrainTimes · Product board" (https://app.notion.com/p/4107cd9e1320815c95bed6694390e203, database "TrainTimes tickets"). Each Notion card links its issue in the "GitHub issue" field; each issue links its card.
- Build sequence and blockers: [`docs/BUILD-ORDER.md`](docs/BUILD-ORDER.md). Do not start a ticket while a blocker is open, including an open question in `docs/DECISIONS.md` marked "needed by" that ticket.
- Decisions and open questions: [`docs/DECISIONS.md`](docs/DECISIONS.md). Follow every decision; if a ticket needs a new one, add it there in the same PR.
- Behaviour: [`design/Screen-Requirements.md`](design/Screen-Requirements.md) (its Acceptance checks are the QA list). Look: [`design/frames/`](design/frames/). Handoff files: [`design/handoff/`](design/handoff/).

## Per-ticket workflow

**Speed first (Grigor, 2026-11-07): startup style.** Build only what the ticket's acceptance criteria need; no extras, no gold-plating. Keep both reviews to a quick pass, one round unless something is actually broken, and keep PR bodies and reports short.

1. **Before writing code**, move the Notion card Status to `In progress` and make sure the GitHub issue is open and assigned, so Grigor can follow progress on the board.
2. Read the issue, its Notion card, the frames and the requirements sections it names, and `docs/DECISIONS.md`.
3. Implement on a branch. Open a PR whose body starts with `Closes #N` (or `Part of #N` while an acceptance criterion only Grigor can meet is still open), links the Notion card, and (for UI tickets) shows simulator screenshots next to the frame images.
4. Run **two separate review passes** on the PR:
   - **QA review:** correctness, edge cases, tests, build and CI pass, the ticket's acceptance criteria and Definition of done.
   - **Design review:** compare the result against the ticket's design frames and the requirements doc (layout, tokens, copy, states, light and dark).
   - **Device scope (Grigor, 2026-11-07):** test and review on **iPhone 17 Pro only**. Skip accessibility (VoiceOver, Dynamic Type, large text) and iPad layout in reviews and tests, even where an issue's Definition of done lists them (D23).
5. Fix the findings. If the first round found major issues, run one more round of both reviews. **Two rounds maximum**, then ship.
6. Comment the review outcome on the issue, then **merge the PR yourself** (squash) once the reviews are done and CI is green, and move the Notion card to `Done` (Grigor, 2026-11-07: "merge all PRs, do not wait for me"). Then continue with the next ticket in build order. Stop and tell Grigor only when you hit a blocker you cannot clear (an open "needed by" question, something only he can do, or a red CI you cannot fix).
7. Report back after each ticket: Notion card status, PR link, and the outcome of each review round.
8. **One ticket per session.** A session implements exactly one ticket. When its PR is merged, report back and stop; the next ticket starts in a new session so each one begins with a fresh context (Grigor, 2026-11-07, to save tokens). Anything the next session needs goes in this file, `docs/DECISIONS.md` or the issue, not in chat.

Notion Status values, in order: Backlog, Needs design, Design review, To do, In progress, PR review, Feature QA, Done.

### Architecture

- **MVVM.** Views hold layout only, no business logic. Each screen has an `@Observable @MainActor final class` view model that gets its dependencies as protocols through `init` (repositories, clock, formatter), so tests inject fakes.
- **Repositories return domain types** from `Sources/Core`, never feed or JSON types. Fixture and live implementations sit behind the same protocol (D20).
- **One time formatter** (TT-106) for every time on screen, in VoiceOver and in notifications (D17); tabular digits.
- **Schedule data** (TT-130, D35): the app reads GO Transit's GTFS feed through `GTFSScheduleRepository` (`Sources/Core/Schedule/GTFS`), which also serves the station list. `GTFSFeedStore` downloads the feed on first use, imports rail only, keeps the last good import in Application Support and refreshes it weekly. `ScheduleDependencies.app()` picks it; Xcode previews, the unit test host and UI tests get the fixtures instead. Line notices come from GO's GTFS-realtime Alerts feed (TT-132, D37), read like live status below.
- **Live status** (TT-131, D36): `GTFSRealtimeStore` (`Sources/Core/Schedule/Realtime`) fetches GO's GTFS-realtime TripUpdates feed and `GTFSScheduleRepository` maps it onto the route's trips. **The app ships no Metrolinx key** (TT-179, D88): `GTFSRealtimeStore.relay()` reads TripUpdates and Alerts from the alert server (`/v1/live/trip-updates`, `/v1/live/alerts`), which holds the key as its secret `METROLINX_API_KEY` and fetches each GO feed at most once per 30 s for everyone (`server/src/relay.ts`); a 503 from it shows Offline. Train positions come the same way: `RelayTrainPositions` (`/v1/trains`, JSON) is `ScheduleDependencies.trains`, passed to the ride engine and the automatic ride's watch. Platforms come the same way (TT-225, D104): `PlatformStore` reads `/v1/live/platforms?stop=<origin>` (GO's per-station departures board, which the feeds lack; for Union the Worker also reads GO's Union departures list, whose pair wins, every platform written "7/8", TT-245, D122) and `LiveSnapshot.platforms` puts them on today's trains by GO trip number. Never put the key in the app or the repo. **Boarding at the platform** (TT-233, D114): `BoardingRule` (`Sources/Core/Schedule/BoardingRule.swift`, pure) is the one rule for when a train on Today is Boarding and when it has left: Boarding while GO's train feed places it within 350 m of the route's origin, not more than 2 min ago, with its platform posted, also past its time; departed when the origin has dropped out of its TripUpdates (from 1 min before its time) or its position is farther away once its time has come; with no fresh position the clock, as before. Its facts are `Departure.originFix` and `hasLeftOrigin`, which `Departure.resolve` copies on Today (never offline) from `LiveSnapshot.originFixes` and `leftOrigin`; `GTFSScheduleRepository.liveStatus` fills those from `RelayTrainPositions` (`trains:`, only trains from 45 min before to 90 min after their scheduled time) and `TripUpdate.hasLeft(_:)`. Every "has it left" or "is it boarding" check goes through `departure.hasLeft(at:)`, `departure.isBoarding(at:)` or `BoardingRule.phase(of:now:)`, never `departureTime <= now`. Fixture runs have no fixes, so they follow the clock; Settings › Testing › Live data › Board (`MockLive.boarding`, `-settings.mockLive boarding`) shows it. The alert server's minute cycle runs the same rule (`boardingPhase` in `server/src/activity.ts`, station places in `server/src/stations.ts`): change both together. Unit tests: `BoardingRuleTests`, `OriginSightingTests`. Tests replay the samples in `Tests/UnitTests/Core/Realtime` (`FeedReplay`, written by `scripts/make-realtime-samples.py`; `alerts-*.pb` for line notices). UI tests that need the line notice launch with `XCUIApplication.onDelayedFixture()` and `LaunchArguments.noDismissedNotices`.
- **Alert server** (TT-140, D38, D43): `server/`, a Cloudflare Worker with D1 in TypeScript, its own project outside the Xcode project, on the Workers Free plan (10 ms of CPU per run: keep the minute cycle lean). GitHub Actions uploads the timetable daily (`.github/workflows/server-timetable.yml`). Its minute cycle decides Boarding and the left moment for alerted trains with the app's rule (`boardingPhase`, TT-233, D114: one VehiclePosition decode a cycle, at most two station boards, where a train stands first, then where alerted trains are still to leave, so the card's pill shows the platform from the start, TT-245, D122; `MAX_SENDS` 35 so a run stays under 50 outside requests, Union's board costing one call more). **Time to board** (TT-247, D124): the card's update that first reaches `isBoardTime` (Boarding, or 5 min or less on its minutes, whichever first) carries "Time to board the 4:29 PM train" and goes three times, `ECHO_MS` apart (`BOARD_BUZZES`; `echo` sends each alerting update its count, the question `ASK_BUZZES` 2); once per train through the `BOARDED` mark at the front of `shown` (`boardedIn`), never for a card first seen inside it; server only, the app adds nothing. Test with `cd server && npm ci && npm test && npm run typecheck` (Node 22.18 or later, works on Linux); CI runs `.github/workflows/server.yml` when `server/`, the handoff strings or the sample feeds change. Its `notif.*` copy must match `design/handoff/Localizable.strings` word for word (a test checks). Setup, secrets and deploy: `server/README.md`.
- **Notification taps** (TT-144, D39): `AppDelegate` (`Sources/App`) is the notification centre's delegate and hands each tap's `NotificationLink` (`Sources/Core/Notifications`, parsed from the server's `tripId`/`serviceDate`/`originId`/`destinationId` or `ruleId`) to `AppRouter.open(_:)`; `RootView` opens Trip details or the Alerts tab. UI tests launch as if by a tap with `XCUIApplication.onFixtures(notification:)` (`TT_NOTIFICATION`, Debug only). The watched-trip strip reads `WatchedTripsProviding` (`Sources/Core/Alerts`), which the alert rules store conforms to.
- **Alert rules** (TT-141, D40): `AlertRules` (`Sources/Core/Alerts`), one instance made in `RootView` and shared by the bells, Trip details, the Alerts tab and the watched-trip strip. It keeps rules on device (`alerts.rules`, read once at launch) and saves them on the alert server (`HTTPAlertServer`) after registering the APNs token (`SystemPushRegistration`, fed by `AppDelegate`). `state(of:)` is the only source for On. **One alert per train card** (TT-189, D70): `alert(for:on:)`, the alert that covers a train on its day (a This-trip alert, or a Repeat alert for its usual train on one of its days), is the one lookup; the bell, Trip details (`TripDetailsViewModel(alerts:)`), the watched-trip strip and Live mode read only it, through `WatchedTripsProviding` (`isWatched(_:on:)`, switched on and On; `isAlerted(_:on:)`, switched on), which `RootView` passes to `ScheduleViewModel` and Trip details. A bell tap acts on that alert (a repeating one is switched off with its days, a left-out day is added to it), Repeat saves under the same id, and doubles are merged at launch and after each save. **The bell's capsule** (TT-191, D71): `AlertBellModel` (`Sources/Features/Schedule`) saves through `AlertRules.commit(_:)` (nothing half-kept: a new alert the server cannot take is removed, a change goes back) and shows its result as `capsule` (Alert on with Repeat, Alert off with Undo, Couldn’t … with Try again); Repeat opens the day panel (`repeatTapped()`, `toggleDay(_:)`, `closePanel()`), whose tiles save one change at a time in their own task, so unit tests wait for them. UI test ids: `alert.capsule`, `alert.capsule.action`, `alert.panel`, `alert.panel.days`, `alert.day.N` (ISO weekday), `alert.panel.done`. `AlertDependencies.app()` gives previews, the unit test host and UI tests `FixtureAlertServer` and a fixture token. ### Building and CI

- CI (`.github/workflows/ci.yml`) runs `scripts/ci-test.sh` on every pull request and on main, on GitHub's Xcode 27 image (`runs-on: xcode-27`) with Xcode 27.2 (`DEVELOPER_DIR`), so builds use the iOS 27 SDK App Store Connect asks for (TT-241, D119; the TestFlight workflow uses the same image and Xcode). The tests run on an iPhone 17 Pro simulator on iOS 26.5 (`SIMULATOR_OS`), the runtime the snapshot references were recorded on: the image ships iOS 27 runtimes only, so CI downloads 26.5 first (about 2.5 min), and `ci-test.sh` creates the iPhone 17 Pro, which the image lacks. A run takes about 45 min. Run the same script on a Mac to test locally (`SIMULATOR_OS=26.5` to match CI). On a failure it prints xcodebuild's own last lines, the result bundle's summary and the newest crash report of the app, since cloud sessions cannot download the TestResults artifact (two TT-243 runs ended with exit 65 and no result in the formatted log). When the simulator itself fails under the tests ("Invalid device state", "cannot determine the runtime bundle"), the script restarts it and runs the tests once more, and xcodebuild's test timeouts fail a hung test after 10 min instead of letting it run the job out.
- **Snapshot references are recorded by CI**, since cloud sessions run on Linux without Xcode. Add a snapshot test without a reference and push: CI records the missing image, commits it to the PR branch as "Record reference snapshots… [skip ci]", re-runs the tests against it in the same job and posts the result as the "CI / Build and test" status on that commit, so the PR head shows green or red without a new run. Pull before pushing again, and look at the recorded PNGs in the PR diff during the design review. The recording pass and the re-run share the job's limit (90 min since D119; 60 before), so a run that records can be cancelled in its re-run ("The operation was canceled", status "Tests re-run against the recorded snapshots" failed, no test failure in the log; PR #156): push the next commit and that run, with every reference present, runs one pass. A changed snapshot is never re-recorded automatically: delete the old reference in the PR to have CI record the new one. References are excluded from the test bundle (`*.png` in `EXCLUDED_SOURCE_FILE_NAMES`).
- **UI test waits on slow runners**: some runners are 2 to 6 times slower than others (the UI suite took 458 s on one and 928 s on another, same tree). A query's first check takes about a second on a Mac, so a 5 s wait after a tap or a launch can time out with the right value already on screen (`RecentRoutesTests` turned main red after TT-164 this way; the app was not slower). Give such waits 15 s.
- **Glass snapshot noise**: a snapshot that draws the Liquid Glass bar (`glassSnapshotPrecision`, `drawHierarchyInKeyWindow`) can still miss its tolerance on a runner. On PR #79 `testScheduleTabLight` failed in the recording pass and passed in the re-run, and `testAlertOnDark` failed the other way round, on the same tree; on PR #117 `AlertsSnapshotTests.testAlertsDark` passed in the recording pass and failed in the re-run. A snapshot that fails in only one of the two passes is that noise: push a new commit to run CI again, and do not delete its reference. The swap button's dark glass failed `ScheduleStatesSnapshotTests` in both attempts of one run (a different state each time, and on other branches before), so that suite sets `\.rendersGlass` false like Trip details (TT-166). Before PR #124 many of these failures were the colour-encoding problem `.comparedAsRecorded` fixes (a constant 0.9159375 or similar in light, only saturated pixels off), so read the numbers before calling a failure glass noise.
- **Mock time snapshots follow the date**: the system compact date picker on Settings › Testing draws slightly differently from one UTC day to the next (its pills moved at 00:00 UTC on Nov 10 and again on Nov 11, on every branch), so `testTestingMockTimeLight`/`Dark` can fail in both passes after a midnight with no code change. Delete the failing reference in the PR to have CI record it again. A lasting fix (keeping the system picker out of the compared pixels) is not built yet.
- **TestFlight** (TT-154, D47): Actions › TestFlight › Run workflow archives `main` and uploads it (`scripts/testflight.sh`, signing through `scripts/asc-signing.mjs` with the `ASC_*` API key secrets); build number = run number, version from `MARKETING_VERSION`. The widget extension is signed with its own profile (D67): `asc-signing.mjs` registers its App ID the first time and makes a profile per bundle id, and `testflight.sh` passes them as `TT_APP_PROFILE`/`TT_WIDGETS_PROFILE` (never a global `PROVISIONING_PROFILE_SPECIFIER`). Release builds are only compiled there, and on pull requests that touch its files (unsigned).
- **Squash-merge with your own commit message** (the PR title and `Closes #N`): the default squash message lists the bot's `[skip ci]` commit, and GitHub would then skip CI on main.
- **Never write a skip marker in your own commit messages**, not even to describe one: `[skip ci]`, `[ci skip]`, `[no ci]`, `[skip actions]` or `[actions skip]` anywhere in the message makes GitHub create no CI run for that push, so the PR head has no check. After every push, confirm a run started.
- Moving the tests to a new iOS runtime (`SIMULATOR_OS` in `ci.yml`) redraws snapshots: on iOS 27.2, 261 of 1404 unit tests failed and two UI tests too (D119). Re-record them in one PR by deleting the `__Snapshots__` folders, and look at the new references there.
